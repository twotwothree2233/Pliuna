# Agent Note: 统一桌面打包与包内验收

Status: implemented

## Problem

现有分发脚本只接受 macOS ARM64。
生产依赖、worker 与目标资产需在包内保持一致。
源码冒烟无法覆盖打包后的进程入口和资源路径。
桌面快捷键提示也固定使用 Command 文案。

## Decision

统一入口复用已固定版本的 electron-builder。
只在原生主机制作统一目标表中的候选包。
Linux 必须确认 glibc，不执行未经配置的跨编译。
旧 macOS ARM64 打包与验包入口继续保留。

生产载荷在系统临时目录的独立暂存根准备。
收集器沿实际安装图解析生产依赖，再展开复制。
只选择目标 Monty 包，拒绝版本冲突和未知可选依赖。
SQLite 仅保留运行时 binding、库与许可证。

builder 不再次决定依赖闭包。
暂存 manifest 不携带开发依赖、安装脚本或用户配置。
生产依赖通过显式资源映射复制到 app/node_modules。
复制与结构检查拒绝链接、凭据和数据库。

暂存项目使用空 NPM lock 固定管理器探测。
该锁不声明依赖，也不进入安装包。
这样 Corepack 不会按环境选择并下载默认 pnpm。
真实生产依赖仍只来自已经收集的闭包。

ASAR 当前关闭，所有入口保持普通文件布局。
utilityProcess、监督进程及 Windows Job 模块显式检查。
process-control.js 导出实际进程树和 PluginRpc 模块。
验收脚本直接加载该模块，不加入生产测试后门。

macOS 默认候选格式为 ZIP，Windows 为 NSIS。
Linux 默认 AppImage，三者都支持目录包验收。
Windows 默认当前用户，不请求提升权限。
卸载保留原有用户数据，数据目录和格式不变。

构建显式禁止发布，临时屏蔽签名凭据。
macOS 使用本地临时签名并关闭公证。
签名跳过 Monty 目录，保留上游签名与字节。
构建结束直接比较原始资产字节，不计算文件摘要。

本机 Electron 的 framework 链接已被展开。
验收使用已缓存官方分发重新解压的临时目录。
--electron-dist 可显式指定同版本本地分发。
工具不修补已安装依赖，也不静默下载替代运行时。

桌面使用只读 preload 字段显示实际主机平台。
macOS 保留现有标题栏与 Command 文案。
其他系统使用 Ctrl 文案、系统窗口框及退出菜单。
包内应用忽略开发页面 URL，只加载本地页面。

计算能力继续由现有运行时验收门槛控制。
候选包存在或 binding 可加载不会开放计算。
关闭与退出仍沿用运行时清理确认及失败阻塞。
现有数据格式与默认数据目录保持原样。

新建任务按钮在业务忙碌时禁用。
这与既有快捷键及新建入口的忙碌保护一致。
桌面回归等待按钮恢复，再发送新建快捷键。
弹窗关闭也等待可见状态，不依赖固定延时。

渲染窗口可先于原生权限与运行时 IPC 完成。
首启和重启均先等待只读 maintenance.status 确认。
要求 idle、无恢复错误且 GC 控制可用。
等待最多 15 秒，然后才发送一次业务操作。
业务界面断言仍为 5 秒，总测试仍为 30 秒。
状态或初始化错误仍保留最终失败和原生附件。

## CI isolation and distribution links

四平台 CI 禁用 pnpm 构建副作用缓存。
依赖源码缓存继续使用，Electron 正常安装。
macOS 在签名前检查 framework 三处链接。
链接展开时明确失败，不手工改造上游分发。

文件、进程和包内探针各自保留失败结果。
前置构建和 ABI 切换成功后，独立探针继续。
任一测试失败仍使矩阵任务失败。
流程不使用 continue-on-error 掩盖持久化阻塞。

POSIX 可执行位在 POSIX 原生主机验证。
Windows 对无法保留可执行位的 POSIX 夹具明确拒绝。
Windows 仍验收本机载荷、原生模块及错误目标拒绝。
四个平台都保留实际目录包与包内启动门禁。

桌面测试启动环境彻底移除 ELECTRON_RUN_AS_NODE。
Windows 会把空值视为存在，误以 Node 模式启动。
键名按大小写不敏感规则过滤，避免继承别名。
包内 app-node 仍由生产监督入口显式启用该变量。

桌面失败保留截图和维护状态 JSON 附件。
JSON 先写入测试输出目录，再按路径附加。
仅保存在附件 body 的数据不会被目录上传收集。
读取维护状态有 1.5 秒的取证截止。
附件失败不替代原始断言，也不转成成功。
CI 保留非隐藏文件，避免只剩隐藏运行元数据。

Windows 11 使用现有工作流的独立手动模式。
`windows11_only=true` 跳过原四平台 baseline。
仅调度 Windows/X64 标签，并核对指定主机名。
系统必须为 Windows 11 client，不能回退其他版本。

标准用户验收另设默认关闭的 windows11_standard_user。
它必须与 windows11_only 同开，其他模式和安装关闭。
该模式复用完整入口，原 baseline 整组跳过。
主机与权限先核对，不匹配时应用测试为零。

门禁要求非提升、非 SYSTEM 且无 Administrators SID。
只判断 IsInRole 会接受管理员的过滤令牌。
额外使用固定系统 whoami 的组查询，包含 deny-only。
比较固定 SID，不依赖语言，不上传完整组或账户信息。

要求指定主机、Win11 x64 与有效交互桌面。
未知或无法查询的令牌状态保持失败，不回退为普通模式。
检出准备另设默认关闭的 windows11_checkout_probe_only。
它只配标准账户与指定 Win11 模式，跳过全部依赖和应用。
pre-checkout 内联诊断避免读取尚未检出的脚本。
发现放入独立无后代进程，防止文件查询阻塞 action 主线程。

有限候选只读可访问性，版本执行不调用 shell 或网络。
每个版本最多 3 秒，内部总 20 秒，步骤硬截止 1 分钟。
诊断只接受 PATH 已发现且版本合格的 Git。
固定候选在该诊断内只作取证，不隐式修正 PATH。
路径仅留进程内，并对后续 Git 日志加掩码，不写入附件。

当前标准账户 Git 准备另设默认关闭的 windows11_prepare_git。
只在指定主机、真实标准账户的检出诊断模式显式安装。
先检查本账户 Programs/Git 与 Trellis-Toolchain/Git。
已有合格 AMD64 Git 则复用；未知或非空冲突保持拒绝。
仅缺失时使用固定官方 asset 677312539 的 2.56.0.4。
采用 CURRENTUSER、BashOnly、空组件和 NOICONS。
不写持久 PATH，不联动 Python/VS，不访问旧账户。

后续标准账户 job 仍可对固定位置做 3 秒版本检查。
合格后只写当次 GITHUB_PATH，再由下一步骤原样发现。
下载 180 秒、安装 5 分钟、内部总 535 秒，步骤 10 分钟。
3010 停下待重启；未知、超时及其他退出码均失败。
原始日志留独立临时目录，附件仅脱敏阶段和结果。
子进程环境采用必要项允许列表，不传 GitHub 凭据。

标准模式检出到 run_id/attempt 的全新受控子目录。
源目录先核对在 workspace 内且不存在，未知直接失败。
不再把旧根传给 checkout 清理，不能靠放宽 DACL 继续。
诊断固定精确 checkout 提交，最多 3 分钟，再核对 HEAD。

pnpm 清单、Node 版本与所有 shell cwd 同步 source 路径。
标准模式关闭自动 pnpm 缓存，避免从旧 workspace 探测配置。
普通模式仍为原目录与缓存，原应用截止和失败门禁不变。
准备通过不计应用通过，完整复验在诊断后决定。

完整标准账户验收先运行独立只读工具门禁。
门禁位于pnpm/Node配置与依赖之前，普通模式不变。
脚本windows11-standard-toolchain.cjs不含下载或安装分支。
只读本账户Python候选和机器级VS/SDK，不访问旧账户。
Python以-I/-S/-B核对3.12/x64与venv/ensurepip/ssl。
VS核对2022目标组件、MSBuild和Hostx64/x64工具及运行库。
SDK按注册核对x64头、库和资源工具。
版本进程3秒，注册与vswhere各5秒，子进程总50秒。
步骤硬限1分钟，缺失、未知与超时均在依赖前失败。
35个依赖及应用入口显式要求标准门禁success。
标准模式不调用旧总安装脚本，不自动补齐工具。
齐备后仅临时暴露已验证Python，再执行原完整入口。
结果写脱敏standard-toolchain.json，门禁失败应用0。
原应用截止、失败门禁、A隔离目录和产品行为保持。

标准账户和同名 Runner 的交互启动由本机用户完成。
CI 不创建账户、修改服务或调整目录权限。

该入口仍只使用 A 新隔离目录，默认 HOME 不变。
不绕过源码链接夹具要求，不扩大测试超时。
提升会话结果、门禁取证与标准用户结果分开记录。


环境事实先写 JSON，再进入依赖与测试步骤。
默认只发现和复用已装工具，不自动改装系统组件。
服务会话不关闭 GUI 门槛，原生结果单独保留。
Python 契约依赖放在执行器临时 venv 中。

用户授权后，独立手动开关允许补齐三项工具。
范围为 Git、Python 3.12 x64 和 VS2022 C++/SDK。
脚本先核对 PATH、标准目录及 Python 安装登记。
缺失才从固定官方 HTTPS 来源下载并安装。

安装前后清单和退出码持久化为诊断 JSON。
安装器禁止自动重启，不更改 PowerShell 系统策略。
Git 和 Python 使用用户目录，PATH 只向当前 job 补齐。
安装开关默认关闭，开启时也互斥原四平台矩阵。

Python 官方站下载超时后，使用官方 actions 分发。
只提取其中的 CPython 安装器，仍安装到用户目录。
不执行包装脚本中的旧版本及登记清理。
第三方安装器不继承 GitHub 下载凭据。

首次无 Git 时，checkout 会退化为源码归档。
GitHub 主站连接失败时，不为差异检查再次拉取。
保存原始生成文件，构建后只统一 CRLF 再严格比较。
其他生成变化仍失败，不计算文件摘要。

Windows 11 先按锁文件安装，暂不执行依赖脚本。
再从 @electron/rebuild 解析其固定 node-gyp 入口。
当前 node-gyp 为 11.5.0，tar 锁定为 7.5.22。
显式重建白名单内的三个依赖，仍要求全部成功。

pnpm 10.20.0 内置 node-gyp 同为 11.5.0。
但其 tar 为 7.5.1，不受项目锁文件控制。
第五轮在该入口解包 Node 头文件时出现 ENOENT。
选用锁内工具链后仍需指定 Windows 11 原生复验。

不补丁上游依赖，不删除头文件或忽略解包告警。
工具链版本及入口保存为 dependency-toolchain.json。

Windows 11 先单独重建 SQLite 与 esbuild。
再将同版本 Electron 官方 API 资产放入标准缓存。
第六轮原始下载返回 504，不能据此关闭解包故障。
标准 install.js 仍负责分发校验和解压，错误仍失败。

缓存准备仅核对官方资产来源、大小及 ZIP 格式。
不自行计算文件摘要，不关闭安装器原有校验。
下载来源、版本、状态记录为 electron-download.json。
不同依赖顺序构建，避免下载故障遮蔽 SQLite 结果。

Windows 11 的单次启动探针使用独立手动开关。
默认关闭，开启时同样互斥原 baseline 与整套验收。
探针包装真实 ACL 调用计时，不改变其执行语义。
单次诊断预算独立，不放宽全套文件钩子或断言。

Runner 关闭事件只读提取指定时间窗内的相关类别。
只查 Runner 日志尾部与相关服务事件，不读凭据。
不保存原始诊断消息或完整环境，触发者未证实则未知。
Runner 中断不能解释此前已经发生的初始化钩子超时。

独立进程与目录包模式默认关闭，并与启动诊断互斥。
它补齐未运行的 Node/Electron、GUI 及目录包入口。
该模式跳过已知文件阻塞，不能改记第七轮或全验收。
常规文件入口与原有超时、断言和最终门禁保持不变。
单次探针增加空 PowerShell 基线，区分启动与 ACL 开销。
Win11 原生初始化约 16.7 秒，10 次 ACL 占约 99%。
独立验证的 Node/Electron 最小 Job 与包内运行探针通过。
完整业务进程有 8 项超时，两条 GUI 均未过就绪截止。
这些失败保留，不能把所选入口或诊断通过记为全验收。
第九轮当时仅形成权限产品适配方案。
后续独立授权见[原生权限适配](../bug-fix/2026-11-08-windows-native-acl.md)。

工具或安装失败时，不进入应用测试或转为成功。
本流程不主动计算或验证文件摘要。

Windows 11 命令使用 CMD，不依赖 .ps1 启动。
环境查询使用 Node action 与只读 PowerShell 命令。
主机的 Restricted 执行策略保持原样。
不使用 Set-ExecutionPolicy 或 Bypass 参数。

源码与包内 GUI 使用不同输出目录。
环境和失败证据上传，不上传应用目录包。
入口提交带 [skip ci]，只手动派发 Windows 11。
新模式仍使用 A 的隔离目录，不改默认格式或 B。

## Alternatives considered

- 复用原工具脚本可减少检查代码。
  但它在pnpm之后执行，文件查询没有共享截止。
  标准模式改用依赖前的独立有界只读门禁。
  代价是维护一份有限候选检查，普通模式保持原脚本。

- 复用总工具安装入口可少写一个准备步骤。
  但它会联动 Python/VS，超出本次 Git-only 范围。
  采用默认关闭的独立前置入口与临时 job PATH。

- 继续逐平台手写打包器，便于细控平台步骤。
  但会重复安装器、依赖与资源布局处理。
  采用已有 builder，旧 Mac 入口保留作回退。
- 立即启用 ASAR，可缩小普通文件暴露面。
  但 worker、监督进程与原生加载已有普通文件契约。
  当前保留路径一致性，矩阵通过后再独立验收 ASAR。
- 由 builder 重新遍历生产依赖，可减少复制代码。
  但会重新引入包管理器探测与可选目标选择。
  改为显式暂存，builder 只处理分发外壳。
- 为本机展开后的 framework 修复链接，可复用依赖目录。
  但会改写上游安装内容，并掩盖分发本身的问题。
  改为显式使用重新解压的同版本官方分发。

- 直接扩大任务出现断言的时限，可容忍冷启动。
  但未区分窗口显示与后端就绪，仍会抢先发送业务。
  改为先等待只读确认，不重发任务创建。

- 单独新增 Windows 11 工作流，文件可完全独立。
  但当前默认分支未登记该入口，无法直接手动派发。
  复用已登记工作流，新增互斥的定向 job。
- 只要求非提升令牌，配置最少。
  但管理员的过滤令牌仍可能满足该条件。
  标准用户入口同时拒绝 deny-only Administrators 组。
- 继续清理或递归放宽旧 workspace，改入口较少。
  但本轮只知道旧清理停滞，已有删除范围与具体原因未知。
  保留旧目录，选择全新检出与独立有界取证。
- 只改 checkout.path，变更行数最少。
  但后续版本、锁文件、缓存和命令仍可能读取旧根。
  同步所有入口并关闭标准模式的自动缓存探测。
- 在 CI 内创建账户或切换令牌，可减少本机准备。
  但涉及账户、凭据与交互桌面权限，超出此入口范围。
  采用本机标准账户启动 Runner，CI 只验证实际条件。
- 将自托管主机放入原四平台矩阵，可少复制步骤。
  但本次明确只测试 Windows 11，不能误触其他平台。
  采用独立 job 与 baseline 互斥条件，保留原矩阵。

## Consequences

统一目标、依赖闭包与包内路径都有检查入口。
包内进程链路不依赖源码 cwd、系统 Node 或 PATH。
代价是普通文件载荷较大，需持续维护入口清单。
显式复制依赖也需在依赖升级时重新审计。

原四平台基线目录包均提供原生运行证据。
Windows 11 提升权限会话已在 c8d61fe 完整通过。
运行 42496582992 仍限 Build26300 与 A 隔离目录。
标准用户门禁已在 42547553223 / ad4f805 取得原生拒绝证据。
Win11 Pro26300/X64、交互 session1，elevated=false。
