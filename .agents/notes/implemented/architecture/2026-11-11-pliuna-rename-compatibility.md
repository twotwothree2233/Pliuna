# Agent Note: Pliuna 全面更名与旧资料兼容

Status: implemented

## Problem

项目新名为 Pliuna，原名称与其他项目冲突。
原名称也出现在持久化记录及跨进程协议中。
直接替换这些记录会破坏旧资料的继续访问。
仓库没有既有决策笔记，本条建立兼容边界。

## Decision

当前产品、协议和构建入口使用 Pliuna 命名。
大小写形式分别为 Pliuna、pliuna、PLIUNA。
兼容规则集中在 src/shared/branding.ts。

- 新资料使用 ~/.pliuna 和 pliuna.sqlite。
- 新目录不存在时，应用沿用已有的 ~/.trellis。
- 显式资料目录优先，两个目录不自动合并。
- 旧资料继续使用原基础库名及选择器记录。
- 同目录存在两种基础库时，业务访问关闭。
- 选择器中的历史基础库名决定副本保护范围。
- 旧资源类型、图片地址及内置插件 ID 仍可读取。
- 新发布内容、插件模板和工具说明使用新名。
- 旧界面偏好可读取，并保存为当前偏好键。
- 当前偏好和当前环境变量优先于旧值。

兼容读取不重写不可变资源或历史快照。
恢复、导出、清理及副本状态继续引用原文件。
Windows 原生对象名长度按前缀长度计算。
这避免更名后的字符数变化导致校验拒绝。

CI 的显式分支引用保持其实际外部标识。
旧 Windows 工具链目录作为安装路径回退保留。
打包和 Git 排除规则覆盖新旧资料目录。
远端仓库和托管工作区路径不由源码更名修改。

## Alternatives considered

### 自动移动旧目录并改名所有数据库

该方案可让历史路径也立即统一为新名。
恢复、导出和副本记录同时保存原文件身份。
文件移动还涉及运行中旧实例及中断恢复。
本次选择保留原位，避免引入新的迁移状态机。

### 只修改可见产品名

该方案对既有行为影响最小。
但协议、环境变量和打包产物仍保留旧命名。
它没有满足统一项目命名的要求。

## Consequences

新资料和新产物具有一致的产品身份。
旧任务及其保护关系能够继续读取和使用。
代价是兼容入口保留有限的旧名称知识。
显式选择当前目录后，不自动合并旧目录内容。

托管项目显示名也使用 Pliuna。
稳定 projectId、仓库地址和工作区路径保持原值。
这些外部标识仍可定位既有会话与工作区。
