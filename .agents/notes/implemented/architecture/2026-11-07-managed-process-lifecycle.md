# Agent Note: 统一进程树与 Monty 生命周期

Status: implemented

## Problem

Monty 使用负 PID，插件只终止直接子进程。
Windows 无法复用 POSIX 进程组操作。
父进程崩溃与 IPC 失联可能留下派生进程。
直接子进程退出也不能确认整树已退出。

## Decision

`src/platform/process-tree.ts` 持有统一接口。
监督入口为相邻的 `process-supervisor.mjs`。
Monty 与插件共享启动、终止和整树退出确认。
业务模块仍持有提交许可、清理占用和旧结果。

监督进程不执行实际计算或插件代码。
它完成纳管后，才接受后端启动消息。
它转接标准流与受控 IPC。
它的环境不包含模型密钥及任意 Node 启动参数。

POSIX 使用独立的监督进程组。
后端和普通派生进程继承该组。
父进程失联时，监督进程终止整个组。
组内进程消失后，父进程才确认清理完成。

## Windows Job Object

Windows 使用最小 N-API 辅助模块。
源码位于 `native/windows-job/`。
模块只提供创建、纳管、查询、终止和关闭。
构建复用现有固定版本的 node-gyp 工具链。

父进程创建唯一命名的 Job Object。
名称冲突即拒绝，不接管既有 Job。
父进程启用 `KILL_ON_JOB_CLOSE`。
唯一持久句柄不继承给监督进程或后端。

监督进程临时打开 Job 并纳管自身。
纳管成功后立即关闭临时句柄。
在此之前不加载或启动实际后端。
纳管失败不回退到单进程终止或 PID 快照。

父进程崩溃时，内核关闭最后一个 Job 句柄。
显式停止使用 `TerminateJobObject`。
查询活跃进程数为零，才确认整树退出。
启动中断时也处理尚未加入 Job 的监督进程。

`verify:windows-job` 是独立最小探针。
它覆盖嵌套 Job、显式终止和父进程强制崩溃。
也覆盖名称冲突与纳管失败时不执行后端。
非 Windows 主机以 `WINDOWS_REQUIRED` 明确拒绝。

探针先于 Windows 的运行时回归执行。
Electron 探针也执行同一组 Job 验证。
本机 macOS 无法执行 Windows 编译及内核验证。
Windows 最小原生 Job 探针已在 CI 通过。
完整业务生命周期和包内链路继续独立验收。

## Lifecycle and publication

取消先废止调用的提交许可，再请求停止。
插件继续保留取消通知与既有宽限期。
超时、撤权和 IPC 失联复用整树终止接口。
旧调用与迟到结果不能重新取得提交许可。

Monty 保留第一个停止原因。
未收到 native worker PID 时仍受外部截止控制。
报告的 worker PID 不作为独立终止目标。
进程所属关系由父进程建立的组或 Job 决定。

监督进程退出不单独释放清理占用。
整树无法确认退出时，原错误和保护继续保留。
插件维护、任务删除与数据库切换仍等待清理。
Monty 关闭流程可以重试确认原执行的清理。

清理重试不改写旧 Call 结果。
它不创建新计算，不重放原有业务。
仍未退出时继续报告清理未确认。
确认退出后才释放占用，允许应用关闭存储。

## Assets and test seams

生产 worker 继续先执行 `montyAssets` 校验。
计算逻辑集中于 `monty/execution.ts`。
生产入口使用固定的既有计算配额。
目标表、完整性元数据和计算能力门槛不变。

测试入口单独调用同一计算逻辑。
它定位原生模块，但不读取文件计算摘要。
它不替换生产入口，也不引入生产绕过开关。
真实计算测试仅在既有已验证目标上执行。

合成摘要替身使用分块编号比较相同内容。
返回值重复编号，保留截取前缀后的区分度。
这样既覆盖资源比较，也覆盖短签名游标检查。
本任务不执行文件哈希或归档摘要校验。

终止流程合并 RPC close 的同步回调重入。
同一调用栈只向进程树发出一次终止请求。
后续显式清理重试仍可重新发出请求。
实际退出确认继续独立于信号发送结果。

Windows 测试夹具用 junction 引用应用原生模块。
测试进程存活时，已加载 DLL 不能删除。
临时目录清理只删除链接，不删除原生模块。
整树 PID 和 Job 退出断言仍独立执行。

## Alternatives considered

- Windows 使用 `taskkill /T /F`，无需原生模块。
  但 PID 树快照留下启动竞争，也不随父进程崩溃生效。
  采用先纳管后启动、由内核关闭句柄清理的 Job。
- 后端启动后再按 PID 加入 Job，接入改动更少。
  但后端可在纳管前产生未受控后代。
  采用固定监督入口先纳管，再启动实际工作。
- 使用原生辅助程序以 suspended 模式启动后端。
  可在恢复主线程前完成纳管，原子性直接。
  但还需重建 Node 与 Electron 的标准流及 IPC。
  采用 N-API 与空监督进程，复用现有 Node 管道。
- POSIX 插件直接使用独立进程组，可少一个进程。
  但外部解释器通常没有宿主 IPC 失联处理。
  采用监督进程，使父进程崩溃也有组清理路径。

## Consequences

停止、超时和失联的进程操作集中到同一处。
业务层继续等待真实清理，不用信号返回值代替。
macOS 使用既有 POSIX 机制及原配额。
代价是每个运行实例增加一个监督进程。

Windows 构建增加一个 N-API 原生模块。
安装包必须携带监督入口与对应平台模块。
当前构建复制到 out，macOS 既有打包复制整目录。
跨平台安装包验收仍留给 E、F 阶段。

可信插件主动脱离 POSIX 进程组仍是信任边界。
进程树接口不提供 OS 沙箱或副作用回滚。
Windows 最小探针覆盖编译及嵌套 Job。
业务文件身份阻塞不能关闭完整 D 验收。
候选平台的计算门槛不随本机验证结果开放。
