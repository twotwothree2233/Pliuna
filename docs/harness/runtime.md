# 请求、执行与停止

RuntimeStore 协调任务、请求队列和 Run。
同一任务最多一个未结束 Run。
不同任务的模型请求由共享调度器分配名额。

## 两类队列

[RequestQueue](../../src/runtime/request-queue.ts)保存业务请求。
请求绑定文本、模型配置选择、资源和导入操作 ID。
同任务队首需要确认时，后续请求不会越过它。

[ModelScheduler](../../src/runtime/model/service.ts)处理网络请求排队。
当前应用并发为 4，渠道并发为 2。
应用模型等待队列最多 100 项。
调度按任务轮转，并检查渠道名额。

业务请求的同任务等待上限为 20。
材料未导入完成时继续等待。
部分失败、资源失效或模型选择变化会转待确认。
用户可选择成功材料、替换导入或重新选择模型。

## Run 生命周期

Run 使用 running、waiting 和明确的终态。
waiting 的原因可为模型排队、审批或宿主确认。
等待必要清理时使用 ending_cleanup。

终止时先撤销提交资格，再取消相关执行。
进程、调用或必要清理未结束时继续保持 waiting。
清理确认后才安装原定终态。

## 模型循环

当前主循环见[agent.ts](../../src/runtime/model/agent.ts)。
它发送真实消息历史和四工具定义。
每次响应与整批工具结果组成完整交互。
工具参数和执行结果分别登记。

收到工具调用时按当前接口解码并执行。
纯文本回复保存到任务记录。
中断输出与完成回复在记录中区分。
完整消息通过对象读取，不依赖近期事件摘要。

## 配额与重试

模型 limits 可配置请求超时、响应体积和 Run 配额。
Run 配额包括时间、模型次数、工具次数和 token。
未填写的可选限制按代码的未设置语义处理。
默认值文件中的数字不应视为全部自动启用。

无输出且满足可重试条件时允许一次有限重试。
已有部分输出、业务工具派发和未知结果独立处理。
上下文超限交给[压缩流程](context-management.md)。
请求用量记录按 request ID 分页查询。

## 取消、停止与恢复

run.cancel 只结束指定 Run。
task.stop 还取消队列、导入和相关插件工作。
任务先进入 stopping，必要清理后进入 stopped。

恢复任务只从 stopped 重新开放执行。
不会恢复旧 Run、旧许可或旧调用。
删除任务先处理运行和保护关系，再移除业务记录。
正式资源的释放走单独确认流程。

重启时旧 Run 中断，等待请求取消。
原调用结果按已记录派发状态分类。
查询原记录不会重放动作。
